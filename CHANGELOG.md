# Changelog

All notable changes to `dsh-modpack` are documented here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning follows [SemVer](https://semver.org/).

## [0.9.0] — 2026-10-28

### Added

- **A version handshake between the two halves, because they are loaded from two different places.** The host half is read when the plugin is applied; the client half is fetched by the browser, which will happily serve yesterday's copy from its cache after an upgrade. That combination is not a bug in either half — it is two different generations of one plugin talking to each other, and every symptom it produces ("the button does nothing", "the file it exports is empty") reads like a plugin bug. `API_VERSION` is now declared in both files and compared once, at load: the host reports it from `GET /diag`, the page compares it against its own copy, and a difference produces one sentence that names the fix (reload; if that does not help, toggle the plugin off and on). The plugin *version* is deliberately not used for this — it changes for documentation and CSS too, and a stale page is only dangerous when the route shapes moved.
- **`scripts/check-future.mjs` — thirty assertions over the half a user actually looks at.** The suite covers the handshake (both numbers equal, `/diag` reports it, the verdict function only calls a stated *difference* a mismatch, and the verdict actually reaches the banner state), the three transport failure modes as three distinct sentences, the page bootstrap being absent or reshaped, one renamed slot key costing one seat rather than both, and a host runtime with no `ctx.inject` still answering `/diag`. It evaluates the shipped source — slices the real functions out of `client.js` and mounts the real plugin into a synthetic context — so a rewrite that keeps the behaviour passes and a rewrite that loses it fails.
- **`scripts/mutate-future.mjs` — nine mutations, all caught**, including the two that a hand-written test would miss: a probe that never answers being treated as a mismatch (which would put a red banner on every older-but-working install), and one failing seat taking the other down with it.
- **A repository, not just a folder.** `scripts/repo-manifest.mjs` is now the single definition of "what belongs in this repository", read by both `scripts/pack.mjs` and `scripts/publish-github.mjs`. Two surfaces, on purpose: `package.json#files` (what npm publishes) and a repo-only list (CI, issue templates, ignore rules, the build tools themselves). Before this, each tool kept its own list, and the 0.6.1 zip shipped a stray diagnostic script for exactly that reason. `scripts/pack.mjs` replaces the pnpm-based packing step, so the release artifacts can be built on a machine that has nothing but Node, and it now fails if a file is listed but missing, if the tarball's root is not `package/`, or if the two docs mention a version other than the one being built.
- **CI, and a reason for it to exist.** `.github/workflows/ci.yml` runs the full check suite and every `mutate-*` script on Node 20 and 22, on Linux and Windows, then builds the tarball and asserts it contains `index.js`, `client.js` and `cordis.patch.yml` — a release that ships a plugin without its entry point installs cleanly and then does nothing, which is the worst possible failure. It never touches a real Harness: the plugin's entire design is to degrade gracefully against unknown runtimes, so the tests mount it against synthetic ones and stay hermetic (no secrets, no desktop app, no network).
- **`CONTRIBUTING.md`, `SECURITY.md`, issue and pull-request templates.** `SECURITY.md` lists all thirteen routes, what each one can do, and the four things a user should know before installing (the apply route installs code; the AI rung sends plugin metadata to the configured model; the online rung asks npm and GitHub; there is no telemetry). `CONTRIBUTING.md` states the five rules the codebase is actually held to, including the one this project learned the hard way: no layout-affecting CSS property in a stateful selector.
- **`UPLOAD-GUIDE.md` rewritten for this release** — the packing step is now one command that needs no pnpm, and every version string in it is checked by `scripts/pack.mjs` rather than by eye.
- **`UPLOAD-GUIDE.md` no longer claims you can drag directories.** It used to say "select all 16 items and drop them on the page"; a reader who tried it reported that the three folders would not go in, and the report is correct rather than user error. GitHub documents folder drag-and-drop, but the browser upload page accepts *files* reliably and directories only sometimes: Firefox ignores them outright, dropping several at once usually admits the first and silently discards the rest, and a repository created with all three check-boxes unticked has no `Add file` button and therefore no drop zone at all. The guide now (a) ticks *Add a README file* when creating the repository so the drop zone exists and the reader's own `README.md` replaces the placeholder, (b) uploads the 13 root files by drag, (c) fills the three directories by typing a `/` into *Create new file* — which is the documented way to make a subdirectory — pasting each file's contents, and then dragging the remaining files into each directory page (five paste steps, three drag steps, all of them ordinary files), and (d) offers GitHub Desktop as the one-shot alternative that commits all 44 files including directories. It also states what skipping the directories actually costs: nothing a user can see, because the release tarball carries `locale` and `scripts`, and `.github` without `scripts` leaves CI red — so those two are both-or-neither.
- **`.gitignore` gets its own upload step, because dragging it fails too.** A second reader report: the dot-prefixed file either gets filtered out of the browser drag or arrives with the leading dot stripped, which turns it into a harmless file called `gitignore` and silently disables every ignore rule. The browser route now creates it with *Add file → Create new file* typing `.gitignore` verbatim, pastes the contents from the local copy, and drops only the remaining twelve root files; the guide, the FAQ and the one-page cheat sheet all say so, and the mistake is called out with its fix (delete the dotless file, recreate).
- **§3.4 of `UPLOAD-GUIDE.md` is now a complete GitHub Desktop walkthrough, not a seven-line sketch.** It tells you to rename the folder to `dsh-modpack` first, because Desktop pre-fills the repository name from the folder name and a Chinese folder name both forces a manual edit and risks publishing under a Chinese repository name. It then covers installation (the Windows installer asks nothing), browser-only authentication (*Continue With Browser* → *Authorize desktop*; GitHub no longer accepts a username and password in the client), *Add an Existing Repository from Your Hard Drive...* → **Choose...** → select the folder without entering it → the `create a repository` link, the three *Create a Repository* fields that must stay unticked (README / Git ignore / License — this project ships all three), checking that Changes lists 44 files, why *Commit to main* is grey (empty Summary), and *Publish repository* with *Keep this code private* unticked and Organization set to None. Recovery notes cover `The repository already exists`, an accidental private publish, an empty Changes list, and a wrongly selected folder; plus how to update later (Commit → Push origin). Button labels were checked against docs.github.com rather than memory: Windows says *Add local repository...*, and the `/`-in-the-filename trick used by the mouse-only route is the documented way to create a subdirectory.

### Changed

- **The README's publishing section says the same thing.** It still leads with `git push` (the fastest route for anyone who has git), but now warns that the web uploader is reliable for files and not for directories, points at the two mouse-only routes, and states the `.github` + `scripts` both-or-neither rule so nobody publishes a repository with a red Actions badge.
- **`packageDir` and `readPackageMeta` agree on where a package lives** — both now walk the same `packageMetaRoots()` list in the same order (see 0.8.4). Carried into this release unchanged; noted here because the forward-compatibility section of the README now documents it as the single lookup.
- **The client registers each seat through `seat()`, which swallows a failure per seat.** `window.__ModuleLoader__` is a Harness implementation detail, not a contract: a build that renames it, moves it, or loads client halves another way used to take the whole Settings dialog down with an uncaught `TypeError` at module scope. Both the loader call and each `ctx.slots.register` are now guarded, and a renamed slot key costs one missing tab and a console warning, never the plugin.

### Fixed

- **A host runtime without `ctx.inject` silently registered nothing.** `whenService` called `ctx.inject` unconditionally; on a build that predates it, the call threw inside `apply` and both the HTTP routes and the three agent tools were never registered — while the plugin still looked loaded. It now falls back to a direct service read, which is no worse than the behaviour it replaces.

### Testing

- 14 check suites and 7 mutation suites (82 mutations) pass. The new pair is described above; `check-compat.mjs` still covers the host half's six synthetic `pluginManager` shapes and five model-service shapes, and `check-layout.mjs` still holds the line on the 0.8.5–0.8.6 layout invariants.
- Verified against the live desktop host: `/diag` reports `apiVersion: 2` and `pluginVersion: 0.9.0`, and the panel loads with the widened dialog and sticky footer from 0.8.6 intact.
- Verified the shipped artifact, not just the source tree: the built tarball was installed into a clean profile with `dsh plugin add`, and the host half was then imported **out of that profile's `node_modules`** and asked for `/diag` — it answered `pluginVersion 0.9.0`, `apiVersion 2`, with zero runtime dependencies. A package that installs cleanly and then does nothing is the failure this catches.

## [0.8.6] — 2026-10-27

### Fixed

- **「应用这个分类」was painted outside the settings dialog, 127px below it, on top of the backdrop.** The 0.8.5 release made the panel taller than its container and put the footer outside the tree's scroller, which fixed the *inner* clipping — but the panel's container is the settings dialog itself, and that dialog scrolls. Measured on the real client at 1440×900: the action row's bottom edge sat at y=990 while the dialog ended at y=850. At 1280×720: 964 against 696. The buttons were in the DOM, were enabled, and `elementFromPoint` returned the backdrop mask rather than the button, so a real click did nothing. `.mpk-autocat-foot` is now `position: sticky; bottom: 0`, pinned to the dialog's scrollport with an opaque background and a hairline top border, so it stays on screen while the proposal above it scrolls. This is the same class of bug as 0.8.5 and it needed the same fix applied one level further out.
- **The sticky footer was resolving against the wrong scroll container, because `.mpk-tree` had `overflow: hidden`.** `overflow: hidden` clips, but it also *creates a scroll container* — so a `position: sticky` descendant sticks to the tree instead of to the dialog, which is why making the footer sticky alone was not enough. `.mpk-tree` now carries `overflow: hidden; overflow: clip`: `clip` clips without creating a scroll container, and `hidden` stays in front of it as the fallback for engines that do not understand `clip`. The rounded corners still cut the node list off exactly as before.
- **The category tree could never be wider than ~525px, because the settings dialog hard-codes `width: 800px`.** "太小了，独占一整行" was not a problem the tree could solve from the inside: at 1440×900 the plugin section was handed 612px of content box and `.mpk-root` measured 559px, no matter what the plugin asked for. The panel now adds `mpk-wide` to `<html>` while it is mounted, and a single scoped rule — `html.mpk-wide [role="dialog"][aria-modal="true"][data-shortcut-modal="settings"] { width: min(1200px, calc(100vw - 64px)) }` — widens the dialog that hosts it. The rule is gated on the class rather than written globally, so every other settings tab keeps the width the product gave it, and the class is removed on unmount. Measured after the fix at the same window size: `.mpk-root` 559px → 959px, `.mpk-tree` → 925px.
- **The `mpk-wide` class is reference-counted rather than a boolean.** The component is registered in two slots, so both instances can be mounted at once; a boolean would let whichever unmounts first strip the class off the other and collapse the dialog mid-session. The effect increments `documentElement.dataset.mpkWide` on mount and decrements on unmount, removing the class only when the count reaches zero.

### Testing

- `scripts/check-layout.mjs` — a seventh section covering the three bugs that only appear in a real window: the tree must clip with `clip` and the `hidden` fallback must come *first* in declaration order, the footer must be `sticky` at `bottom: 0`, and the width rule must be scoped to `html.mpk-wide` with a `min(...)` width in four digits. Source-order assertions are used where the property alone is not enough — a `clip` after `hidden` and a `hidden` after `clip` look identical to a naive declaration scan, and only one of them works.
- `scripts/mutate-layout.mjs` — eight new mutations, twenty-three in total, all caught: the tree clipping with `hidden` alone, the fallback ordered after `clip`, the footer losing `sticky`, the footer pinned to `top`, the dialog keeping its 800px, the width rule losing its `html.mpk-wide` scope, the class never being removed, and the class being removed on any unmount. Two older mutations were re-aimed at the current declarations after the `overflow` and footer rules changed — a mutation whose pattern no longer matches is reported as a survival, which is the correct verdict.
- Verified end-to-end against the live host at 1440×900, 1280×720, 1600×1000 and 1920×1080 with real CDP mouse events, walking the actual user path (account menu → 设置 → 插件整合包 → 自动分类 → 开始分类 → 应用这个分类). At every size and every phase, all five preview buttons report `insideDialog: true` and `reachable: true` with no manual scrolling. Screenshots in `dist/_verify-<W>x<H>.png` on the dev machine only.

## [0.8.5] — 2026-10-27

### Fixed

- **「应用这个分类」was on screen but out of reach, because the panel that grows was inside the box that scrolls.** The category tree was a 300px side rail whose entire content — header, auto-classify panel, node list, footer — lived in one `max-height` + `overflow:auto` box. Clicking 预览 made the panel taller, and everything below it moved down inside a container that had no scrollbar until it overflowed and no visual cue that it could scroll; the wheel over the preview list scrolled *the list*, not the rail. The button existed in the DOM the whole time. The tree is now a card with a scrolling **body** rather than a scrolling card: `.mpk-tree` no longer scrolls at all, only `.mpk-tree-body` does, and the header, the auto-classify panel and the footer sit outside it in source order. Nothing that appears after a click can push anything out of reach, because nothing that grows is inside the scroller.
- **The category column is a full-width row instead of a 300px rail.** A rail narrower than the five-button action row at the bottom of the preview was the other half of the same clipping: the buttons were laid out on one un-wrapping line, overflowed the rail, and were cut off by its scroll container. `.mpk-stack` is a column, so the tree gets the whole width, and the action row wraps as well — the cause is removed twice over.
- **「这些分类可以重命名、合并或删掉，和手动建的完全一样。」no longer breaks into a ragged block.** The footer was a wrapping flex row in which the sentence and the buttons shared line boxes: the sentence was given `flex: 1 1 100%` but the buttons still followed it on the same wrapped line, so at rail width it collapsed into three ragged lines of two or three characters each. The footer is now a `flex-direction: column` with the sentence as a `<p>` on its own line and the buttons in their own wrapping row beneath it — a column cannot produce that failure by construction, which is why it is the shape rather than another `flex-basis` tweak.
- **The auto-classify panel is a band inside the tree card, not a card nested in a card.** Once the rail became a full-width row, a bordered box inside a bordered box read as a mistake; the header rule above it and the footer rule below it already separate it from its neighbours. Closed, it is now just its own button with no tinted band around it.
- **A disabled 应用 button now says why.** It is disabled for exactly one reason — the proposal added nothing — and a disabled button with no explanation is indistinguishable from a broken one, which is how this panel was reported. The tooltip carries the sentence.

### Testing

- `scripts/check-layout.mjs` — extended from the "nothing moves when you click" invariant to the containment invariant that this release is about. The tree card must not scroll, the tree body must, and the auto-classify panel must be emitted **before** the body div in source order — JSX children are positional, so source order is the only thing that decides whether the panel is inside the scroller. The footer must be a column, the action row must wrap, and `.mpk-stack` must be a column rather than a row. Each of these is a shape assertion, not a snapshot: a rewrite that keeps the fix passes, a rewrite that reintroduces the containment bug does not.
- `scripts/mutate-layout.mjs` — five new mutations, fifteen in total, all caught: the tree card scrolling as a whole again, the panel moved back inside the body, the footer going back to a wrapping row, the action row no longer wrapping, and the category column going back to a side rail. This file now also captures the child check's stderr instead of inheriting it — inheriting printed every *expected* failure as though the run had gone wrong.

## [0.8.4] — 2026-10-27

### Fixed

- **The AI rung could not be called at all: every request died before the first token with `signals[0] is not of type AbortSignal.`** The host's `LlmRuntime.prepareCall(config, signal, configure)` ends with `deepFreeze(structuredClone(resolved.config))`, and `structuredClone` of an `AbortSignal` returns a bare object — no prototype, `instanceof` false, `Object.keys` empty. The adapter then does `AbortSignal.any([options.signal, consumer.signal])` and throws on the very first element. `callModel` had been passing the signal as a *config field*; it is a separate second argument to `prepareCall`, and `LlmCallConfig` has no such field. The call is now `prepareCall(base, signal)` with `base` carrying only `provider`/`model`/`messages`/`maxTokens`/`temperature`, and the live signal is re-attached to the `GenerateOptions` object handed to `prepared.stream(...)` — after deleting any inherited copy, so what reaches the adapter is the original object and not a clone. Re-attaching is safe because `callConfigEquals` compares only `provider`, `model`, `reasoningEffort`, `temperature`, `maxTokens` and `stop`; `messages` and `signal` are not part of the comparison, so a prepared call cannot be rejected for carrying them. This is the same shape the runtime's own `dsh-experimental-translation` and auto-review call sites use.
- **The classifier was reading a profile directory that does not exist.** `profileDir()` was `DSH_PROFILE_DIR || <home>/profiles/<DSH_PROFILE || 'default'>`. On the desktop client the host is launched with the profile directory as a *command-line argument*, so neither variable is set in the host process — they are exported into shell calls, not into the plugin sandbox — and the fallback resolved to `<home>/profiles/default`, a directory that does not exist. Nothing failed loudly: the asar-resident official packages still resolved through `packageMetaRoots`, so the machine looked half-classified rather than broken, and the rows that went missing were exactly the ones the user had installed himself. `apply` now records `ctx.get('profileContext').dir` into `profileDirOverride` before anything reads a path, and `profileDir()` prefers it; the environment stays as the fallback because the test harness mounts the plugin without a profile context and drives it that way.
- **Reading a manifest and reading its code disagreed about where a package lives.** `readPackageMeta` searched the profile and then the runtime archive; `packageDir` — the lookup behind `codeDigest` and `roleFacts` — only knew about the profile. A row could therefore be *filed* from its manifest description and still report no source and no role, which is what the panel showed as "0 with source, 0 with a role description" on a machine full of official bundles. `packageDir` now walks the same `packageMetaRoots()` list in the same order: one lookup, one answer.
- **215 of 243 rows — every single Loader entry in a real desktop profile — were filed under 其他.** `pluginRows` built `{key, kind, entryId, moduleName, enabled, ...}` and never set `name`; `classifyRow`, `classifyFromLocalDescription`, `classifyFromLocalReadme`, `codeDigest` and `roleFacts` all read `row.name` or bailed out on `row.kind !== 'bundle'`. The rows were not unclassifiable — 212 of 215 carry a title and 207 a description, straight from the `dsh.meta` block the package registers — the classifier simply never looked. `pluginRows` now sets `name: packageNameOf(p.moduleName)`, and `classifyRow` reads the manifest for any row that names a package rather than only for bundles.
- **A subpath entry is not a package.** The Loader names an entry after the module it loaded, so one package contributes several entries (`@deepseek-ai/dsh-plugin-manager` and its `/tools` subpath). `packageNameOf` cuts the subpath off — `@scope/pkg/sub` → `@scope/pkg` — and returns `null` for `cordis:include`, the Loader's own pseudo-module, which has no `package.json` anywhere. Without this the subpath entries were classified from a name no package ever had, and the pseudo-module would have been read as a package called `cordis`.
- **The AI and online passes were still bundles-only, so on a real profile they had nothing to work on.** Both `aiClassify` and `enrichRemote` picked candidates with `row.kind === 'bundle' && needsRemote(...)`. Once Loader entries started carrying package names they were the *only* rows still landing in 其他 — and they were exactly the rows the expensive passes refused to look at, so the panel reported `candidates: 16, fromAi: 16` while the sixteen rows that needed a judgement were never sent. Both filters now ask the question that actually matters — does this row name a package we could send — via `Boolean(row.name)`, and the Loader entries reach the model with their manifest, code digest and relationship line like any bundle.
- **The description tier only read `package.json`, so Loader entries got nothing even after they had names.** `classifyFromLocalDescription` and `classifyFromLocalReadme` both began with `if (row.kind !== 'bundle') return null`. Both now accept any row with a name. For the description itself the tier prefers what the row already carries — the title and description the plugin registered for itself — and falls back to `package.json#description` only when the row has neither, which is what a bundle row does. The reason sentence names which of the two it read, because "the plugin's own package.json description" is a false claim about a row whose text came from the Loader.
- **The vocabulary was thin enough that even with names and descriptions, 179 of 215 rows would still have been guesses.** `REMOTE_SIGNALS.hints` covered a handful of English terms and almost no Chinese, while the real descriptions are full of 服务, 工具, 界面, 会话, 存储, 网页, 沙箱, 权限, 遥测. The table gained four buckets (`tasks`, `dialogs`, `profiles`, plus `office`/文档转换 under `files`) and the existing ones were filled out; on the dev machine's real profile 其他 went 215 → 1, and the only row left is `cordis:include`, which genuinely has no name, no description and no manifest.

### Testing

The fixture is deliberately hostile: `DSH_PROFILE` names a profile directory that exists and is empty, while the fake `profileContext.dir` names the one holding the package. If `apply` ignored the context the package would be unreachable and the row could only be guessed, which is the bug; the assertion also reads `/diag` to confirm the host reports the launched directory rather than the fallback. A second half mounts the plugin with no profile context at all and checks the environment still decides, so the fix cannot quietly turn into a hard dependency on a service that a plain `node` host does not provide.

Two assertions check that the signal reaching the adapter is a real `AbortSignal` and that it is live rather than a clone, so a regression is caught by an assertion instead of by a TypeError. `promptOf(llm)` replaces six inline prompt reads that threw when the model was never called — a mutation must be killed by an assertion, not by the test crashing. A further scenario covers the widened candidate set: a Loader entry is now offered to the model, asked about, and filed from its answer; the pass used to filter on `row.kind === 'bundle'`, so on a live profile it reported sixteen candidates while all 215 Loader entries were invisible to it. - `scripts/mutate-metasource.mjs` — five new mutations, fifteen in total, all caught: Loader entries given no package name, a subpath entry keeping its subpath as the name, the description tier going back to reading only bundles, the host ignoring the profile the launcher passed in, and the override written but never read back.
- `scripts/mutate-ai.mjs` — two new mutations, eighteen in total, all caught: the signal put back into the config object, and a live signal not re-attached to the stream options. The "every row is sent to the model" mutation was re-aimed at the widened candidate filter — a mutation whose pattern no longer matches is reported as a survival, which is the correct verdict.

## [0.8.3] — 2026-10-27

### Added

- **A fourth rung: the model is told how the plugin attaches to the harness, and asked to reason before it files the row.** The AI pass already saw a package name, a description, some keywords and (optionally) a code excerpt, and the request behind this release was the gap that leaves: a name is a guess and a description is marketing, but *what a plugin registers* is neither. `roleFacts(row, digest)` now derives that from the manifest and the entry file — `halves` (`client+host` / `client` / `host` / `unknown`, from `dsh.client` or an `exports['./client']` entry versus a resolvable `main`), `patch` (`dsh.bundle.patch` present, i.e. this package layers onto an existing feature rather than adding one), `slot` (the literal ids in `slots.register('...')`, up to four) and `touches` (which capabilities the code actually reaches for: `ui`, `http`, `files`, `process`, `llm`, `agent`, `terminal`). The prompt carries it as one line — `relationship: halves=client+host; patch=yes; slot=settings.section; touches=ui,http,files` — explained field by field, followed by an instruction to guess from the name first and then *check that guess against the relationship*, and to write the reasoning into `why`. The preview names the rung and counts the rows that actually carried a line ("N of them came with a role description"), and the per-row reason says "按名字与作用关系推理" / "reasoned from name + role" rather than reusing the plain AI label.
- **The rung is a strict extension of the source rung, and the panel says so by switching source on with it.** The facts come out of the entry file, so ticking the reasoning box ticks source too; the host forces the same thing independently (`source: body.source === true || body.reason === true`) instead of trusting the client to have done it. Switching AI off clears both, because both are instructions to the same model call.

### Fixed

- **A package nothing is known about no longer gets a relationship line describing it as touching nothing.** The first cut of `roleFacts` returned `{halves:'unknown', slot:[], surfaces:[], patch:false}` for every row, which renders as `touches=-` — a sentence nobody verified, and one a model would read as "this plugin does nothing". `roleFacts` now returns `null` unless it learned something (`halves !== 'unknown' || slots.length > 0 || surfaces.length > 0`), and the prompt only explains the field when at least one row carries it, so an absent line reads as *unknown* instead of as a fact.
- **The panel can no longer claim the model reasoned when it did not.** `aiClassify` reports `reasoned` only when the box was ticked **and** at least one `relationship:` line was actually sent (`stats.withRole > 0`). A run over a profile whose manifests are unreadable spends the tokens, sends no relationship, and now says so.

### Testing

- `scripts/check-ai.mjs` — extended. A new `unlabelled-delta` fixture whose name and description decide nothing, whose manifest declares both a browser half and a bundle patch, and whose entry file mounts a settings slot and opens an HTTP route: the only thing that can tell the model it is a settings panel is the `relationship` line, so the scenario notices if that line stops being sent. Scenario 5b asserts the rung's whole contract — the entry file is read even with `source` unticked, `halves=client+host`, `patch=yes`, `slot=settings.section`, `touches` containing both `files` and `http` and `ui`, the field explanations, the "guess first, then check" instruction, the "write the reasoning into why" instruction, `withRole >= 1` and `reasoned === true`. Scenario 5c is its mirror (source on, reason off: code present, no relationship line, no instruction, `reasoned === false`). Scenario 5d runs against a second profile whose `node_modules` carries no manifests at all, and asserts the opposite failure: the model is still called, no line is attached, and `reasoned === false && withRole === 0`. Every assertion about an absent line reads one plugin's block rather than the whole prompt, because a lazy regex over the prompt happily matches the *next* plugin's line — a bug this file hit and now has a `blockOf` helper for.

- **A “how do I send this” panel after every export**, listing the three routes (they have the plugin / they don't / by hand) and offering a ready-to-paste message for the recipient's agent, built from the very document that was just written so the two cannot disagree. Copying falls back to a hidden textarea when the shell withholds clipboard access.

### Why

A user asked the obvious question about the whole feature: *does the person I send a pack to also need this plugin installed?* For the one-click path, yes — and that is a bootstrap problem, because a pack cannot install the tool you need to open it. It is only a problem for the UI route, though: every DSH ships `pluginManager` and every agent can call it, so the pack was always installable without us. Nothing said so. That silence was the defect.

## [0.2.0] — 2026-10-26

### Added

- **Category tree** — a nestable, user-named tree over the installed plugins, shown beside the plugin list in the builder. Create a category with `＋`, add a child from any node's hover tools, rename in place, delete with confirmation. Deleting a category moves its children up to the grandparent and returns its plugins to **Uncategorized** rather than deleting them.
- **Assignment from the list** — every plugin row carries a *Move to* selector showing the tree indented, so a plugin can be re-parented without leaving the list. With rows checked, the footer's bulk selector moves the whole selection at once.
- **Scope filtering** — clicking a category narrows the list to that subtree (a parent counts everything beneath it); **Uncategorized** shows what has not been filed yet. The existing search and chips still apply on top, so "disabled plugins in 语言模型" is one click.
- **Select this category** — selects a whole subtree at once, because a parent category is normally a heading over its children.
- **Grouping travels with the pack** — export stamps each plugin with its full category path (`语言模型 / 国内`) and lists the categories used in the document, so a pack stays readable to whoever receives it. `planModpack` ignores it: it is documentation, never an install instruction.
- `scripts/check-categories.mjs` — drives the real routes against a throwaway DSH home. It exists because `categories.json` sits in the user's home directory and people will hand-edit, sync and merge it, so the interesting inputs are the broken ones: cycles, dangling parents, self-parents, assignments pointing at deleted categories. It also asserts that a refused save leaves the stored tree untouched. The cycle assertion was mutation-checked — with the cycle breaker disabled, the suite fails.
- `scripts/check-tree-logic.mjs` — slices the tree walkers' *actual source* out of `client.js` and evaluates it, because a re-implementation here would only prove the copy works. It covers ordering (including the equal-`order` name tiebreak), subtree scoping, path labelling, a dangling parent, and a cyclic document the UI might briefly hold before the host's repaired copy arrives. A watchdog turns a hang into a visible failure, since a broken cycle guard would otherwise stall rather than fail. Mutation-checked: with descent removed from `subtreeIds`, two assertions fail.

### Design notes

- Storage is `<DSH_HOME>/storages/dsh-modpack/categories.json`, a flat `nodes[]` list with `parentId` rather than a nested document. Every edit becomes a map over one array, and a corrupt file can never produce a structure the renderer's walk cannot terminate on.
- The host sanitizes on both read and write: ids de-duplicated, names bounded, dangling and self parents detached, cycles broken by detaching the node that closed them (leaving the rest of the subtree where the user put it), and assignments to non-existent categories dropped. What sanitizing cannot honestly repair — a blank name, a duplicate id, a non-object document — is refused *before* writing, so a refusal never destroys the tree already on disk.
- Saves are serialized through a single promise chain on the client, because two quick renames would otherwise race and whichever response landed last would win, writing back a tree the user had already moved past. The UI updates optimistically and resyncs from disk if a save fails.
- The tree lives beside the plugin list in a two-column split rather than on its own tab: filing plugins and picking them for a pack are the same activity, and separating them would mean a tab switch per drag.

## [0.1.1] — 2026-10-26

Both fixes below come from one user report: *“重启了但是我在插件页看到没有变化”* — after a restart, nothing had changed. Every automated check up to that point had passed, because each one tested the code in isolation instead of the code against a real runtime.

### Fixed

- **The host half never registered anything.** `webServer` and `tools` were read with `ctx.get()` inside `apply()`. That call reports only what is mounted *at that instant*, and both services are regularly mounted **after** plugins are applied — so the probe returned `undefined`, both registrations were skipped, and the plugin still looked healthy: the UI rendered and every request behind it failed. They now go through `ctx.inject([name], cb)`, which declares the dependency and fires when the service arrives. A `whenService(ctx, name, cb)` helper keeps a `ctx.get` fallback for runtimes that predate `inject`.
- **The UI had no seat.** The panel registered into `settings.plugins.tab`, and the registration was genuinely accepted — the live slot tree showed `id: modpack, order: 50, active: true`. But the shipped Plugins page renders **no tab strip**, so the contribution was accepted and never drawn. The panel now registers into `settings.section` (id `modpack`, order 16 — directly after Plugins), the seat that actually renders and the one the installed `billion-context` plugin occupies. The `settings.plugins.tab` registration is kept as cheap insurance for builds that do draw tabs.

### Changed

- `README.md` documents where the UI actually appears and why the tab slot is not used.

## [0.1.0] — 2026-10-26

First release. Verified against DeepSeek Harness `0.2.1-rc.3` on Windows (Node 24.21.0).

### Added

- **Modpack builder tab** — registers into the `settings.plugins.tab` slot (id `modpack`, order 50), so it sits beside the built-in plugin inventory under **Settings → Plugins**. No shipped id is replaced (`replaceRisk: none`).
- **Inventory** — one checkable row per bundle and per live Loader entry, sourced from the `pluginManager` Host service (`listBundles` / `listPlugins`), including version, install spec, availability, enablement, official/optional/removable flags, row counts and declared overrides.
- **Filtering** — live search over name, module name and description, plus filters for enabled / disabled / local-link / official / removable, with select-all, select-none and “only shareable”.
- **Export** — builds a portable `.dshmodpack.json` document (format `dsh-modpack`, `formatVersion` 1) carrying pack name, author, pack version, description, generator stamp, source `dshVersion` and per-plugin enablement and patch overrides.
- **Non-portable detection** — `link:` / `file:` / absolute-path specs are flagged as `notPortable` before export, because they cannot resolve on another machine.
- **Import** — load a `.dshmodpack.json` (from disk or from the saved list), review a dry-run plan, then install.
- **Install** — goes through `pluginManager.installBundle` for absent packages and `setBundleEnabled` for enablement changes; nothing rewrites `package.json`, `cordis.patch.yml` or `node_modules` by hand.
- **Version pinning** — an opt-in *Pin versions* switch installs each bundle at the exact version the pack records, instead of resolving the recorded range. Off by default, because a range survives an unpublished version while a pin reproduces the author's setup exactly. Local-path entries are never pinned.
- **Saved modpacks** — packs can be written to `<DSH_HOME>/storages/dsh-modpack` and re-listed, loaded or deleted from the UI.
- **Agent tools** — `modpack_list`, `modpack_export`, `modpack_apply`, so an agent can drive the same flow.
- **Bilingual UI** — Chinese and English, following the active client locale.
- **Host HTTP API** — a single `webServer` prefix route at `/api/dsh-modpack` with `diag`, `inventory`, `saved`, `pack`, `save`, `load`, `delete`, `plan` and `apply`.

### Fixed

- **Exported specs are now resolvable.** A profile's `dependencies` map stores a bare range (`^0.1.208`), which the filesystem fallback exported verbatim; importing such a pack handed `installBundle` a nameless range that npm cannot resolve. Registry ranges are now qualified as `name@range` at export, and `planModpack` re-qualifies any nameless range on the way in, so hand-edited and older packs import correctly too. `link:` / `file:` / git / URL specs are passed through untouched.
- **Honest install preview.** The dry-run plan used to say “将安装 0.1.208” while actually resolving the recorded range; each install row now states whether it will resolve a range or install a pin.
- **Agent tools actually register.** The three tools were built with `defineTool` from `@deepseek-ai/dsh-tools`, which is not a resolvable specifier for a profile-installed plugin. The dynamic import threw, the surrounding `catch` swallowed it, and because the plugin still loaded and served its UI, nothing looked broken while the tools never existed at all. They are now plain `ToolDefinition` objects carrying raw JSON Schema — the host projects `parameters` verbatim to the model and validates only that `output.render` is a function and `output.schema` is a supported JSON Schema, so nothing else was ever needed. `scripts/check-tools.mjs` mounts the host half against a context that exposes only `tools` and fails if any tool stops reaching `tools.register`.

### Hardened

- Every request is gated by `connection.admit()`; the route reports `legacy` when the service is absent rather than failing open silently.
- Every `ctx.get()` is guarded, so the plugin still loads on a Harness build that lacks a service.
- **Filesystem fallback** — when no `pluginManager` service exists, the inventory is built read-only from the profile's `package.json` (dependencies + `dsh.profile.bundles`) and `cordis.patch.yml` disable flags, so exporting still works; installation is refused and the UI says so.
- Body reads are capped, and the load/delete endpoints reject any filename containing a path separator or `..`.

### Known limitations

- Installing a modpack requires a Harness build that exposes `pluginManager`. Without it the tab is view-and-export only.
- A modpack is a list of install instructions, not vendored code: a `link:` entry from someone else's machine cannot be reproduced and is reported as non-portable at export time.
- Plugin *configuration* inside a pack is carried as the raw `cordis.patch.yml` row; conflicting local configuration is surfaced in the preview rather than silently replaced.
